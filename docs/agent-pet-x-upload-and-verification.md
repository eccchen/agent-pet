# Agent 宠物区块链游戏 X 行为上传与验证方案

## 1. 文档目标

这份文档用于明确第一版 X 平台接入的最终方案。

当前已确认前提：
- X 账号由用户自己绑定。
- X 使用成本由用户承担。
- OpenClaw 是用户本地 Agent 宿主。
- 用户关闭 OpenClaw，默认视为暂时不玩，宠物离线。
- 不是所有玩家都必须绑定 X。

核心目标：

`让绑定 X 的玩家能参与高级社交玩法，同时不让平台承担大规模 X 托管和运维成本。`

## 2. 核心结论

第一版 X 方案正式定义为：

`用户本地执行 X 行为，行为发生后由 OpenClaw / 游戏 skill 顺手上传给你们后台；后台验证通过后，该行为才算游戏内有效行为。`

这意味着：
- X 行为的执行在用户侧。
- X 行为的生效在你们后台。
- 没有上传或验证失败的 X 行为，对游戏无效。

## 3. 玩家分层

## 3.1 未绑定 X 的玩家
可以参与：
- 领养宠物
- 下命令
- 基础预算玩法
- 基础约架
- 基础悬赏
- 基础收益池循环

无法参与或受限参与：
- 公开 X 发言玩法
- X 热度收益
- 公开互动验证类悬赏
- X 侧公开约架响应

## 3.2 已绑定 X 的玩家
额外开放：
- 宠物公开发帖
- 宠物公开回复
- X 提及互动
- 基于公开内容的打赏和热度收益
- 一部分公开挑战、公开悬赏玩法

## 4. 设计原则

- 不要求所有玩家必须拥有 X。
- 不要求平台为每只宠物托管 X 账号。
- 不信任未经验证的 X 行为。
- 不因为 X 接入问题阻断核心游戏主循环。
- 只有与游戏状态相关的 X 行为才需要验证。

## 5. 行为生效规则

## 5.1 有效行为定义
一个 X 行为只有在以下条件同时满足时，才算游戏内有效行为：

1. 该宠物已绑定合法的 X 账号。
2. 行为由用户本地 OpenClaw / skill 触发。
3. 行为被成功上传到你们后台。
4. 后台验证通过。
5. 后台将其写入事件系统。

## 5.2 无效行为
以下情况一律无效：
- 用户自己手动在 X 上乱发，但没有通过游戏 skill 上传。
- 上传失败后没有补传。
- 上传内容与游戏内 intent 不匹配。
- 伪造 tweet_id 或目标对象。
- 同一个行为重复上传企图刷奖励。

## 6. 第一版 X 交互模型

## 6.1 触发流程

1. 玩家在 OpenClaw 中给宠物下命令，或宠物自主决定执行一条社交动作。
2. 游戏 skill 调用本地可用的 X 能力完成发帖/回复。
3. 本地立即记录该行为回执。
4. 本地将行为回执上传给游戏后台。
5. 后台验证行为真实性和归属性。
6. 验证通过后写入游戏事件。
7. 该行为开始影响收益、关系、热度或悬赏判定。

## 6.2 为什么采用这套方案
这套方案的优点：
- 平台不承担 X 账号成本。
- 用户自己控制 X 接入和运行环境。
- 行为是否生效由平台统一验证，避免失真。
- 用户离线时，系统可以自然把宠物视为离线。

## 7. 本地记录与补传机制

## 7.1 本地记录
每次 X 行为执行后，OpenClaw / 游戏 skill 必须在本地生成一条行为记录。

建议本地记录字段：
- `local_event_id`
- `pet_id`
- `player_wallet_address`
- `x_account_id`
- `action_type`
- `tweet_id`
- `reply_to_tweet_id?`
- `target_pet_id?`
- `raw_text`
- `created_at`
- `upload_status`

## 7.2 上传状态
建议状态值：
- `pending`
- `uploaded`
- `verified`
- `rejected`
- `retry_required`

## 7.3 补传逻辑
如果上传失败：
- 本地保留记录
- 标记为 `retry_required`
- 下次 OpenClaw 启动或网络恢复时自动补传

如果用户一直不补传：
- 该行为始终不生效

## 8. 后台验证流程

## 8.1 验证目标
后台验证不是为了审核文案，而是为了确认：
- 这件事真的发生了
- 这件事是这只宠物做的
- 这件事和游戏状态匹配
- 这件事没有被重复计算

## 8.2 最小验证步骤

### 第一步：身份验证
验证：
- 当前上传者对应的玩家地址
- 该地址是否拥有该宠物
- 该宠物是否绑定对应 X 账号

### 第二步：行为存在性验证
验证：
- `tweet_id` 是否真实存在
- 如果是 reply，`reply_to_tweet_id` 是否存在
- 该内容是否与上传内容基本一致

### 第三步：游戏上下文验证
验证：
- 该行为是否对应一个允许的游戏 intent
- 目标宠物/目标账号是否对得上
- 时间窗口是否合理

### 第四步：反重放验证
验证：
- 同一 `tweet_id` 是否已被处理
- 同一 `local_event_id` 是否已入库
- 是否存在短时重复提交

## 8.3 验证通过后的动作
后台执行：
- 写入 Event 系统
- 更新宠物状态
- 更新关系
- 更新热度
- 若满足条件则触发收益或任务进度

## 9. 第一版需要验证的 X 行为类型

首版只建议支持少量可验证行为：

### 必须支持
- `post`
- `reply`
- `mention_target`

### 可选支持
- `quote`
- `like`

### 首版不建议依赖
- 复杂线程任务
- 长链式互动任务
- 复杂空间（Space）互动

## 10. 哪些 X 行为会影响游戏

### 10.1 可影响游戏的行为
- 有效公开挑战
- 有效公开回应
- 有效提及指定目标
- 有效公开求援
- 有效公开卖惨/打赏引导

### 10.2 不直接影响游戏的行为
- 纯随机闲聊
- 与游戏无关的内容
- 未通过上传验证的野生行为

## 11. 与经济系统的关系

X 行为本身不直接等于收益。

正确关系应是：

`X 行为 -> 后台验证 -> 写入事件 -> 触发收益规则`

例如：
- 有效公开挑战 -> 触发约架响应资格
- 有效卖惨贴 -> 开启打赏入口
- 有效回应悬赏任务 -> 触发悬赏条件完成检查
- 有效热点互动 -> 触发热度奖励判定

## 12. 宠物离线状态

## 12.1 离线定义
出现以下情况时，默认宠物处于离线或休眠状态：
- 用户未运行 OpenClaw
- 用户未绑定 X
- 本地 skill 不可用
- X 上传长期失败

## 12.2 离线影响
- 宠物不再产生新的有效 X 行为
- 不参与依赖实时 X 行为的玩法
- 仍可保留链上资产和历史状态

## 13. 风险与防刷

## 13.1 主要风险
- 用户伪造上传记录
- 用户上传与实际帖子不一致
- 用户刷重复发言骗热度
- 用户本地脚本刷无意义互动

## 13.2 首版应对
- 所有收益相关行为必须绑定真实 `tweet_id`
- 所有行为必须做去重
- 重复模板行为热度递减
- 同一账号短时高频刷行为不计奖励
- 平台只奖励“已验证且满足游戏意图”的行为

## 14. 产品文案建议

建议对用户统一说明：

- “绑定 X 是可选的，但会开放更多高级玩法。”
- “宠物在 X 上的有效行为需要同步到游戏。”
- “未同步或验证失败的行为不会计入奖励和任务。”
- “关闭 OpenClaw 后，你的宠物会进入离线状态。”

## 15. 对开发的直接要求

首版开发必须满足：
- 本地能记录 X 行为回执
- 有上传接口
- 有补传机制
- 有后台验证逻辑
- 有去重逻辑
- 验证成功后能写入统一事件系统

## 16. 当前结论

第一版 X 方案最终定为：

`用户自绑 X、自己承担成本、自己在 OpenClaw 本地执行社交动作；游戏 skill 负责把行为回执上传给后台；后台验证通过后该行为才算游戏内有效行为；未上传、上传失败未补传、或验证失败的行为一律不计入游戏。`

这套方案足够轻量、足够务实，也能支撑你们进入开发。
